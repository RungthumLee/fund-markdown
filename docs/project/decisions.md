## DEC-001 — ดึงข้อมูลแบบ bulk ไม่ใช่ per-fund

**บริบท:** ต้องเก็บ ~2,300 กอง × 21 endpoints

**ตัดสินใจ:** เรียก endpoint โดย **ไม่ส่ง `proj_id`** แล้ววน cursor เอาทั้งตลาด

**เหตุผล:** ลดจำนวน request จาก ~48,000 เหลือ ~2,000 (เร็วขึ้น ~24 เท่า)

**ทางเลือกที่ไม่เลือก:** per-fund loop — ตรงไปตรงมากว่าแต่ใช้เวลา ~16 ชม.
และต้องจัดการ retry รายกอง

**ผลข้างเคียง:** ไฟล์ raw ใหญ่ (ดู [[issues|ISS-003]]) และต้อง group by เอง

## DEC-003 — กรอง scope ที่ระดับโครงการ ไม่ใช่ระดับ share class

**บริบท:** 1 `proj_id` มีได้หลาย share class และแต่ละ class มี attribute ของตัวเอง

**ตัดสินใจ:** ถ้ามี class ใด class หนึ่งเข้าข่าย Term fund หรือ PVD → ตัดทั้งโครงการ

**เหตุผล:** attribute `proj_term_flag` และ `proj_retail_type` เป็นคุณสมบัติของ
**โครงการ** ไม่ใช่ของ class การตัดครึ่ง ๆ กลาง ๆ จะได้โน้ตที่ข้อมูลไม่ครบ

**ข้อควรระวัง:** ถ้าในอนาคต SEC ใส่ค่าต่างกันระหว่าง class จริง ๆ ต้องทบทวนข้อนี้
ตอนนี้ `transform.py` บันทึกทุกกองที่ถูกตัดพร้อมเหตุผลไว้ที่ `data/processed/excluded.json`

## DEC-010 — ผลค้นเว็บใช้หา ISIN เท่านั้น ไม่ใช้เป็นแหล่งตัวเลข

**บริบท:** หลัง Yahoo+FT จบ ยังมีกองหลักที่ไม่มีข้อมูล
คำถามคือใช้ผลค้นเว็บ / AI Overview เติมได้ไหม

**ตัดสินใจ:** ใช้ได้ แต่แยกเป็นสองทาง
1. **ISIN** ที่ค้นเจอ → ยืนยันกับ FT (USD/EUR/GBP) และ Yahoo
   ผ่านแล้วจึงกลายเป็นข้อมูลปกติเต็มรูปแบบ · ยืนยันไม่ได้ = ทิ้ง
2. **ตัวเลข/คำบรรยาย** ที่ยืนยันไม่ได้ → เก็บใน `search_facts` / `search_note`
   แสดงในบล็อก `[!CAUTION]` แยก ติด tag `#web-search`
   และ**ไม่มี index หรือตารางเปรียบเทียบใดอ่านค่าพวกนี้**

**เหตุผล:** วัดผลแล้ว บทสรุปจากผลค้นปนตัวเลขข้าม share class
(GMO Quality: ผลค้น 1.05%/7.8bn vs FT ของ class จริง 0.53%/6.61bn GBP)
กองทุนหลักเป็น share class เฉพาะเจาะจงเสมอ ตัวเลขที่ปนจึงผิดในทางที่อันตราย —
มันเข้าไปจัดอันดับในตารางค่าธรรมเนียมได้ ดู [[issues|ISS-014]]

**ทางเลือกที่ไม่เลือก:**
- เก็บตัวเลขจากผลค้นเป็นข้อมูลปกติ — เร็วกว่ามาก แต่ทำลายความเชื่อถือของตารางเทียบค่าธรรมเนียม
- ไม่ใช้ผลค้นเลย — เสียโอกาส เพราะการหา ISIN มันทำได้ดีจริง (12 จาก 19 กองที่ทดสอบ)

**ผล:** กองที่ไม่มีข้อมูล 111 → 89 (แก้บั๊ก 10 + ค้นเว็บ 12)
ดู [[../guides/web-search-enrichment|Web Search Enrichment]]

## DEC-011 — รวมชื่อสินทรัพย์ด้วย ISIN + exact key เท่านั้น ไม่ใช้ fuzzy matching

**บริบท:** สินทรัพย์ตัวเดียวถูกสะกดได้ถึง 29 แบบ (SPDR Gold Shares)
ทำให้ตัวเลขกระจุกตัวต่ำกว่าจริง และตอบไม่ได้ว่ากองไหนถือหุ้นตัวไหนบ้าง

**ตัดสินใจ:** สามชั้น
1. ISIN ตรงกัน = entity เดียวกัน (59% ของแถว)
2. ไม่มี ISIN → normalized name key ที่**ตรงกันเป๊ะ**เท่านั้น
3. ชื่อที่แสดงเลือกจาก**คะแนนคุณภาพ** ไม่ใช่ความถี่

**เหตุผลที่ไม่ใช้ fuzzy:** edit-distance จะยุบ `CP ALL` เข้ากับ `CP AXTRA`
และ `TISCO` เข้ากับ `TASCO` ซึ่งเป็นคนละบริษัท
การรวมผิดตรวจจับยากกว่าการไม่รวม และทำให้ข้อมูลผิดแบบเงียบ ๆ

**เหตุผลที่ไม่โหวตตามความถี่:** ทองคำจะได้ชื่อว่า `B046RT1 US`
เพราะ SEDOL บังเอิญพบบ่อยที่สุด — จึงให้คะแนนตามลักษณะของสตริงแทน

**ผล:** ชื่อดิบ 26,586 → entity 4,488 · ยุบชื่อซ้ำ 5,969 รายการ
ดู [[../guides/entity-normalization|Entity Normalization]]

## DEC-012 — แยก `daily.py` ออกจาก `run_all.py`

และของที่มีค่าจริงในรอบที่สองคือ**ส่วนต่าง** ไม่ใช่โน้ต 7,000 ฉบับที่ถูกเขียนทับ

- ใส่ `--force` ใน cron — ได้ ~45 นาทีและ ~2,000 API call ทุกวันโดยไม่จำเป็น
- ใช้ hash เนื้อไฟล์แทน mtime — hash ข้อมูลดิบหลายร้อย MB แพงกว่า stage ที่จะข้าม

**ผล:** วันที่ไม่มีอะไรเปลี่ยน ~10 วินาที · วันที่ NAV ขยับ ~40 วินาที

## DEC-015 — ใช้ OpenFIGI เป็นระบบรหัสสินทรัพย์ ไม่ใช่ Finnhub หรือ FMP

**บริบท:** ต้องการยืนยันชื่อ ประเภท และ ticker ของสินทรัพย์จากแหล่งที่เป็นกลาง

**ตัดสินใจ:** OpenFIGI (Bloomberg) — ทดสอบทั้งสามเจ้าด้วย ISIN จริงก่อนเลือก

**เหตุผลเชิงตัวเลข:**
- **Finnhub** — ISIN ต้องมี entitlement · international coverage อยู่ในแผนเสียเงิน
  ข้อมูลเราเป็นไทย 1,597 บวก LU/IE/SG/VN/MY/JP แทบทั้งหมด
- **FMP** — 250 ครั้ง/วัน = **13 วัน** ต่อหนึ่งรอบ 3,357 รายการ
  และการแสดงข้อมูลต่อสาธารณะต้องมี licensing agreement
- **OpenFIGI** — 8/8 ในการทดสอบ · มี key ได้ 100 job/request · **91 วินาที** ต่อรอบ

**ผล:** ผูกได้ 3,026 (90%) · ชื่อดีขึ้น 238 · ประเภทไม่ตรงกับที่ บลจ. ยื่น 70

**ข้อจำกัดที่ยอมรับ:** OpenFIGI **ไม่คืน ISIN** (map ISIN → FIGI ทางเดียว)
จึงหา ISIN ให้สินทรัพย์ที่ไม่มีไม่ได้ · ไม่มีราคา/AUM/ค่าธรรมเนียม
ส่วนนั้นยังพึ่ง Yahoo + FT

## DEC-016 — ไม่แก้ `kind` ตาม OpenFIGI แต่ขึ้นคำเตือนแทน

**บริบท:** OpenFIGI ไม่เห็นด้วยกับที่ บลจ. ยื่น 70 รายการ
ส่วนใหญ่คือ REIT ที่ถูกยื่นเป็นหน่วยลงทุนหรือหุ้น

**ตัดสินใจ:** เก็บ `figi_type` ไว้เป็นข้อมูลประกอบ **ไม่เปลี่ยน `kind`**
แล้วขึ้นกล่อง `[!WARNING]` ในโน้ต 38 ฉบับที่ไม่ตรงกัน

**เหตุผล:** `kind` เป็นส่วนหนึ่งของ `entity_id` (`equity:CLAR` / `reit:CLAR`)
การเปลี่ยนจะทำให้ทุกลิงก์ในวอลต์พัง และข้อมูล ก.ล.ต. ก็คือสิ่งที่ บลจ. ยื่นจริง
การแสดงทั้งสองฝั่งซื่อตรงกว่าการเลือกข้างเงียบ ๆ
